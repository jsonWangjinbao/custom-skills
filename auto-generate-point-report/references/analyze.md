# 业务价值筛选与证据分析（进入阶段 3 时读取）

## 1. 先选题，后下钻

先读 kpi.json 的当前窗 docKpis、regressiveByStep、failByEvent、环节耗时/漏斗定位信号，再通过 SLS 明细验证问题；不另用原始行聚合替换核心指标。
按「受影响单据/账号范围 × 是否阻断业务 × 是否可行动」排序；次数是参考，不套未经认可的分数模型。
默认按证据选 3–8 项深挖；不足则少写，不能凑满。剩余问题列待观察及缺少证据。

可入周报的三类问题：
1. **业务规则/供给约束**：可约额度、时段、状态限制反复打回，说明受影响范围和规则是否能在操作前暴露。
2. **流程/交互成本**：已完成业务状态仍允许无效入口、空列表无后续、重复点击、频繁返回/重填；需行为序列及字段证据。
3. **操作/数据质量**：司机字段校验、账号操作集中、特定仓库/组织反复失败；先验证口径，再提出可操作建议。

采集截断、事件重复、缺失原因或新版本未覆盖属于「可观测性缺口」，不直接认定业务故障。
PV 高但未操作可能只是查看，取消可能是合理撤回，低闭环可能是跨周未完结；不得直接写成缺陷。

## 2. 最小证据包

每项入选问题需：
- 一句话事实 + 业务影响，附范围/分母；少量严重样本也应明确样本数。
- 动作结果：success / fail / validate_fail / cancel / unknown；完成提交数、接口失败率、表单打回率、合计异常率。
- 单据范围：涉及单据、异常单据、异常率、窗口内失败后成功数、窗口内未见成功数。
- 根因到报文级：`api_code` + `api_msg` 原文关键句 + 占比，表单层再给字段与字段组合。
- 时间/组织/账号/仓库分布与主要原因；账号用 ID 优先、组织隔离，无 ID 的姓名不证明唯一自然人。
- 代表单据：总提交、失败次数/率、跨度、提交密度、事件序列、窗口内结局，证据定位至事件 key。
- 业务解释与建议；代码或产品事实尚未确认时标「待验证」，不是根因实锤。

evidence.json 字段对应（写报告时直接取用，不自行重算）：
- 节点级：`businessMetrics`（双口径与覆盖率）、`dailyProfile`（days/hours/zeroHours/fullDayCount/peakHours/busiestDay/quietestDay）、`regressionTop`（回退操作 TOP）、`stateTransitions`（事件自报状态迁移）、`traceOutcomes`（来自核心指标侧）、`pageRawEvents`、`sharedIpSources`。
- 动作级（`actions[]`）：`metrics`、`rootCauses`（layer/apiCode/reason/message/count/pctOfAbnormal）、`durations`（samples/p50Ms/p90Ms/maxMs/atFrontEndTimeout）、`docRetry`（单均/p50/p90/max/topDocuments/topDocumentCadence）、`organizations`、`stores`（store + storeName）、`accounts[]`（metrics/activeMs/topReasons/peakHours/ipSources）、`fields`/`fieldCombinations`、`days`/`hours`、`docOutcomes`、`sampleDocs`、`successfulRegressionCount`。

kpi.json 保存同 computeRunId 的核心指标与口径版本（analyzerVersion/analyzerDigest/configFingerprint）；其比例字段通常为 0–1，转百分比展示时按实际值乘 100，不与明细百分比字段混用。
check 门禁与 quality.json 决定允许措辞；整节点与环节/单据明细分别标范围、来源和分母，不把一个局部失败率称为整节点核心指标。

## 3. 双口径定义（数字由脚本计算）

- 完成提交 = success + fail + validate_fail；接口失败率 = fail / 完成提交；表单打回率 = validate_fail / 完成提交。
- 合计异常次数 = fail + validate_fail；合计异常率 = 合计异常次数 / 完成提交。cancel/unknown 不加分母，但单列数量。
- 涉及单据 = 当前动作全部可关联单据去重；异常单据 = 经历 fail/validate_fail 的单据去重；异常率 = 异常 / 涉及。
- 只成功单据必须计分母；无 FID 单据用类型+单号回退并记录覆盖率，不能把空 FID 当一张单据。
- 一个批量动作可关联多张单据，动作层只计一次；各单据计一次关联，不能反向相加成动作数。
- 失败后成功 = 同一动作+单据的成功时间晚于失败时间；此前成功不能算后来失败恢复。
- 未见成功 = 观察窗口中失败后无更晚成功；不是永久卡死，也不等于业务全链闭环。

闭环率、一次通过率、平均返工、卡单和漏斗来自本地复用的看板分析器结果，不在 Python 重写；成功回退按节点 regressiveCodes 识别，失败尝试不算真实返工。
比率最多保留小数点后 4 位：本地一次遍历与看板流式累加存在 1 ULP 末位差（已对拍定量），不得写成数据不一致；并列计数项（如 failByEvent 同 count）无稳定顺序，引用前按 count 降序 + 名称二次排序。
核心指标计算限定整节点或所选 FID，不支持环节级 KPI；选预约发货环节时，总览仍标整节点，专项只分析配置里该 step 的事件。
配置 category 是业务分类，不证明子应用归属；实际 app.name 用 apps 清单匹配，未知或歧义必须暂停。

## 4. 定向深挖路由

| 信号 | 追加分析 | 不可跳过的反证 |
| --- | --- | --- |
| 高频业务失败 | `rootCauses` 按 api_code + 报文原文归纳，保留阈值/配额/日期数值与占比 | 同动作成功分母、受影响单据数；报文模板不等于实际请求量 |
| 表单打回 | `fieldCombinations` 与 details，字段组合、各单结局 | 缺字段不猜；字段命中不一定是留空，需 details/样本值验证 |
| empty_items 等软失败 | 状态、结果码、明细返回和随后操作 | API 说 success 不证明用户业务成功；没有界面证据不声称无提示 |
| 重试/连点 | `docRetry` 的单均/p50/p90/max + `topDocumentCadence` 中位间隔；单据×trace×time 排序 | 重复上报先去重；自动重试与人工点击需采集或代码确认 |
| 接口耗时 | `durations` 的 p50/p90/max 与 60 秒触顶数，配 fail 率 | 均值被长尾拉高时必报中位；触顶后的服务端结局不可知，不猜 |
| 账号集中 | `accounts[]` 双口径 + `topReasons` + `peakHours`；`organizations` 给组织集中度 | 不把账号当自然人，不因失败次数高判定能力低 |
| 账号共用怀疑 | 开 includeIp 新范围，账号×IP 与 IP×账号、时间覆盖 | NAT/代理/动态 IP/网络切换：IP 数≠人数≠设备数；报告只写脱敏 IP |
| 仓库/配额集中 | `stores`（store + storeName）与报文披露的上限值/热门日期 | 报文未披露阈值时不自行推算配额；store_id 与名称一起给 |
| 时间/组织集中 | `dailyProfile` 逐日与峰值小时，对照成功日/时段；`zeroHours` 只在完整自然日判定 | 当前版本不查询前窗、不做环比或同比；归零小时可能是低谷也可能是中断，写清判据 |
| 回退/返工 | `regressionTop` 按事件名×次数，对照同类成功量给比例 | 回退是合法操作，不默认是缺陷；失败尝试不算真实返工 |
| 状态异常迁移 | `stateTransitions` 找逆向与「通过后作废/驳回」类迁移，再回核心指标的状态边对照 | 事件自报迁移与核心指标状态边不同源，不混算；无上下游关联证据不推断跨系统影响 |

接口大载荷（api_params/response）不在默认投影；SLS 分析字段可能截断，空值不证明空返回。
确需回查时，由 Agent 在授权的少量事件键范围用既有只读原始日志工具取样，记录样本覆盖，不将 SDK 或未知原文塞进报告。
历史版本代码/页面材料只在必要时读当前用户授权项目，不跨仓库硬依赖路径。

## 5. 本对话的方法沉淀（不预设结论）

- 核心统计定位信号，再深挖预约确认与司机字段打回；报告保持问题导向，而非大图表堆叠。
- 人员表扩展总操作次数/失败率、涉及/异常单据/异常率与行为画像，区分高频重试和广泛受阻。
- 单据表补成功分母，逐单还原卡点；从「反复失败」追到「窗口内是否恢复」，避免误判永久卡死。
- 校验字段按组合、长尾账号和单据结局分析；两段校验的关系需同一单据序列证实。
- IP 辅助账号来源分类，**纠正旧结论**：不能据一个 IP 宣称个人行为实锤，也不能据两个不重叠 IP 宣称两人轮班。
- 新旧底稿出现数量差，先核对事件范围、去重和结束时刻；不能未经逐项对账说全部一致。

## 6. 防止失焦

不自动开发修复，不替运营联系供应商，不发外部消息；只交付可验证发现与建议。
对「高频」的业务解释不确定时，标注需要确认的规则/场景，不另启动调试或代码修复 skill。
本阶段只读分析指南；输出前再加载 report.md，避免一次读全流程。
